# Migration to the project Remotion license declaration

Nothing breaks and nothing has to be migrated. The declaration gate is
unchanged in substance: Remotion still cannot be used until the user says which
license applies to them. What changed is where that statement can live.

## Before

`workflow init --remotion-license DECLARATION` wrote the statement into that
edit's `workflow-state.json`. It was correct but not durable: a second
recording, or the same recording in a new session with a new workspace, asked
again.

## Now

A project can record the statement once:

```bash
social-video-agent remotion-license attest free_license_eligible \
  --project-root . --accept-terms
```

It is stored in `.social-video/remotion-license.json`, next to the project
config but deliberately not inside it — `config.yaml` is branding, is edited to
change how videos look, and is reasonable to copy between projects. A licensing
statement is none of those things.

The file records the declaration, the acknowledgement, the moment, who declared
(if given), the component versions in effect, and the terms URL the statement
was made against. It records nothing else: eligibility is never derived from
company size, revenue, funding or any other signal, and there is no field in
which such a signal could be supplied.

## Precedence

`workflow init` and `render` resolve in this order:

1. an explicit `--remotion-license` flag — declares for that one edit and
   overrides whatever is stored;
2. this edit's own `workflow-state.json`, when resuming (`render` only);
3. the project's stored declaration;
4. nothing — the command stops and prints how to record one.

## Existing workspaces

An edit created before this change keeps working untouched. Its
`workflow-state.json` already carries `remotion_license_attestation`, that value
is still authoritative when resuming, and no declaration file is consulted or
required. New states additionally record `remotion_license_source`
(`cli_flag` or `project_declaration`); a state without that field is read as
"declared for this edit only", which is exactly what it was.

Adopting the project file is optional and does not invalidate anything:

```bash
social-video-agent remotion-license status --project-root .
social-video-agent remotion-license attest DECLARATION --project-root . --accept-terms
```

## Re-confirmation, refresh and revocation

A stored declaration stops being usable — and the workflow asks again — when it
was revoked, when it names different terms than the build points at, when it
was made under an older release line, or when it is more than a year old. The
message says which of those happened.

```bash
social-video-agent remotion-license refresh --project-root . --accept-terms
social-video-agent remotion-license revoke --project-root . --reason "yearly review"
```

A revoked declaration is never reinstated by a refresh; making the statement
again is a deliberate act (`attest ... --replace`). Revoking does not touch
workspaces that already recorded their own declaration.

## Not the agent's statement to make

`--accept-terms` records that a person read the terms and is declaring for
themselves. An assistant must ask the user, use the answer given, and never
supply the acknowledgement on their behalf — the same rule that already applies
to `license_confirmed` for music and sound effects.
